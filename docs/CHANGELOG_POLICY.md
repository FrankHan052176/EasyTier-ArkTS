# 更新记录维护方案

应用内更新记录分为“正式版”和“开发版”两条渠道，二者不能混用发布日期或版本号。

## 正式版

- 只在 AppGallery 正式版本发布后新增记录，版本号和日期以实际发布信息为准。
- 每条记录描述相对上一个正式版新增的用户可见能力与重要修复，发布后不再改写。
- 正式版页面只展示“正式版”、版本号和构建日期，不展示开发渠道或测试下载入口。
- 正式版记录不使用开发版测试链接。

## 开发版

- 数组顶部只保留一条滚动更新的开发版记录，基线指向最近一个正式版。
- 仅记录已合入主线、可以由开发版构建获得的变化；更新内容时同步更新日期和
  `CHANGELOG_REVISION`。
- “获取开发版”始终跳转到 AppGallery 测试页：
  `https://appgallery.huawei.com/apptest/2MsGy1dzT1T`。

开发版由 `main` push、Core `repository_dispatch` 或手动 workflow 触发；它们都使用
`product=publish` 和发布签名，但由构建渠道常量标记为 `development`。

## 正式版构建

- 正式版只由 GitHub `release.published` 事件触发，Release tag 必须与正式版版本号一致。
- 正式版同样使用 `product=publish` 和发布签名，不能用签名类型判断渠道。
- 构建时直接把顶部最新的开发版记录提升为当前正式版，使用 App 版本号和 Release 发布日期，
  并移除开发版下载链接；后面的历史正式记录保持不变。
- Action 会将签名 App 上传到 AGC 并等待包处理成功，但不创建、更新或提交 AGC 测试版本。
- 正式 AppGallery 版本由发布者在 AGC 中人工创建和提交。

## 正式发布流程

1. 验收顶部开发版记录，并创建与目标 App 版本号一致的 GitHub Release。
2. Release 构建自动把该开发记录提升为正式记录，无需复制更新内容。
3. 发布后在主线把该条记录转为历史正式记录，并在顶部新增下一轮开发版记录。
4. 每次更新记录内容都递增 `CHANGELOG_REVISION`，确保本地 Debug 固定使用
   `0.0.1 / 99999999` 时也只会重新展示一次最新记录。
